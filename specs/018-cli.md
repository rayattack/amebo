# 018 — CLI

## Summary

`amebo` is a single binary with subcommands powered by `spf13/cobra`. The CLI both runs the server and drives administrative actions against a running cluster.

## Command tree

```
amebo
├── serve                       # run the server
├── version                     # print version + build info
├── init                        # initialize a new data dir (writes default amebo.yaml)
├── cluster
│   ├── status                  # cluster topology
│   ├── join                    # add a peer to the cluster (runs from a fresh node)
│   ├── leave                   # remove self from the cluster
│   ├── force-remove            # remove a dead peer (emergency)
│   ├── snapshot
│   │   ├── create              # trigger a snapshot
│   │   ├── list                # list local snapshots
│   │   └── restore             # restore from a snapshot file (offline)
│   └── transfer-leadership     # transfer leadership to another node
├── admin
│   ├── reset-password          # reset the admin password via local socket (leader only)
│   ├── rotate-master-key       # rotate AMEBO_SECRET; rewrap secrets at rest
│   └── audit                   # dump audit log (future)
├── actions
│   ├── validate                # offline validate a schema file
│   └── list                    # list actions (server required)
├── apps
│   ├── create
│   ├── list
│   └── toggle
├── events
│   └── publish                 # CLI-side event publishing helper (signs with app secret)
├── gists
│   ├── replay                  # replay one or many
│   └── acknowledge
└── import
    └── python                  # import data from a Python amebo Postgres dump (spec 021)
```

## Global flags

Applied to every subcommand:

- `--config <path>`: config file (default `./amebo.yaml` if present).
- `--addr <url>`: target server for remote subcommands (default `http://localhost:3310`).
- `--secret <value>`: `AMEBO_SECRET` for cluster ops (env-preferred; flag for ad-hoc).
- `--json`: emit JSON output instead of human-readable tables.
- `--quiet`: suppress non-error output.
- `--verbose`: include debug lines from client-side.

## `amebo serve`

Starts the server. All config keys in spec 003 are mapped to flags with matching kebab-case names.

Exit codes:
- 0: clean shutdown.
- 1: fatal startup error.
- 2: config validation error.

## `amebo init`

Creates `data/` directory, writes a populated `amebo.yaml` with placeholder values and generated defaults (random `AMEBO_SECRET`, `NODE_ID=<hostname>`). Prints next steps.

```
$ amebo init --data-dir /var/lib/amebo
✓ wrote /var/lib/amebo/amebo.yaml
✓ generated AMEBO_SECRET (export it securely)
✓ run `amebo serve --config /var/lib/amebo/amebo.yaml --bootstrap` to start the first node
```

## `amebo cluster status`

```
$ amebo cluster status --addr http://10.0.0.1:3310
NODE     STATE     RAFT_ADDR          HTTP_ADDR          APPLIED    LAST_CONTACT
node-1   Leader    10.0.0.1:3410      10.0.0.1:3310      12345      -
node-2   Follower  10.0.0.2:3410      10.0.0.2:3310      12345      120ms
node-3   Follower  10.0.0.3:3410      10.0.0.3:3310      12340      1.2s

Term: 4    Commit index: 12345    Leader: node-1
```

With `--json`, emits the same data as spec 007's status response.

## `amebo cluster join`

Run on a **fresh node** with an empty data dir. Exits 0 after the node catches up enough to accept traffic.

```
$ amebo cluster join --addr http://10.0.0.1:3310 --secret $SECRET \
                    --node-id node-4 --raft-addr 10.0.0.4:3410
→ POST /v1/cluster/join to http://10.0.0.1:3310
✓ added as voter; catching up...
✓ applied index 12345 of 12345
✓ node-4 is now a member
```

## `amebo cluster leave --self`

Graceful removal. Continues serving reads until SIGTERM.

## `amebo admin reset-password`

**Runs on the leader's host** — connects via `$DATA_DIR/admin.sock` (unix domain socket). This is how to recover if the admin password is lost.

```
$ sudo amebo admin reset-password --data-dir /var/lib/amebo
New password: ****
Confirm: ****
✓ admin password updated (replicated across cluster)
```

If run on a follower, prints the leader address and exits.

## `amebo actions validate`

Client-side schema validation, no server needed:

```
$ amebo actions validate --schema ./my-schema.json
✓ valid Draft 2020-12 schema (2341 bytes)

$ amebo actions validate --schema ./broken.json
✗ invalid: "type" must be a string or an array at $.type
```

Useful in CI pipelines.

## `amebo events publish`

Signs and POSTs an event using an app's secret — convenience for scripts and testing:

```
$ amebo events publish \
    --app billing --secret $APP_SECRET \
    --action v1.customers.created \
    --deduper cust-123 \
    --payload '{"customer_id":"c123","amount":42}'
```

Reads `--payload-file` if the payload is large. Includes timestamp, nonce, signature headers automatically.

## `amebo import python`

See spec 021. Reads a Postgres dump or a running Python amebo's admin API and replays the data via Raft into the Go cluster.

## Shell completion

`amebo completion bash|zsh|fish|powershell` — cobra's built-in.

## Help

`amebo --help` and `amebo <cmd> --help` show per-command usage. All subcommands document flags and env var names together.

## Exit code conventions

- 0: success.
- 1: generic error.
- 2: usage/config error.
- 3: network/server error.
- 4: auth error.
- 5: partial success (e.g. batch publish with some failures).

## Output format

- Default: human-readable with aligned columns. Color on TTY.
- `--json`: newline-delimited JSON for scripts.
- `--quiet`: only errors.
- Tables use stdlib `tabwriter`; no external deps.

## Acceptance criteria

- [ ] `amebo --help` lists all commands.
- [ ] `amebo version` prints version, commit, build date, go version.
- [ ] `amebo init` on an empty dir produces a working config file.
- [ ] `amebo cluster status` works against a running cluster and returns accurate JSON with `--json`.
- [ ] `amebo actions validate` exits non-zero on invalid schema; matches `/v1/actions` server-side errors.
- [ ] `amebo events publish` end-to-end produces a visible event in the admin UI.
- [ ] `amebo admin reset-password` refuses to run on a follower and directs to the leader.

## Alternatives considered

- **urfave/cli**: cleaner API but less widely used. Cobra's ecosystem (pflag, viper, completion) is worth it.
- **Separate `amebo-cli` binary**: more binaries to ship. Keep it one.
- **Remote-only CLI (no `reset-password` via local socket)**: password recovery requires a local escape hatch. Kept.
